---
title: 리포지토리 생성자에서 DDL을 빼고 스키마 생성을 명시 호출로
date: 2026-09-25
area: [pipeline, backend]
decision: PaperRepository 등 생성자가 매번 실행하던 DDL(DROP TABLE 포함)을 없애고 ensure_schema()와 scripts/migrate_schema.py로 스키마를 한 번 만든다
---

**결정과 근거** — `PaperRepository.__init__`이 생성될 때마다 약 15개의 DDL을 실행했고, 그중에
`DROP TABLE IF EXISTS paper_ai_summaries`가 있었다. 에이전트 도구가 호출마다 리포지토리를 만들었으므로 요청 경로에서
DDL과 테이블 삭제가 반복됐다. 생성자는 연결도 DDL도 만들지 않게 하고, 스키마는 `ensure_schema()`를 명시 호출할 때만 만든다
(dc0981d). 새 DB나 스키마 변경 뒤에는 `scripts/migrate_schema.py`를 한 번 돌리고, prepare-worker는 시작할 때
`ensure_schema()`를 한 번 부른다. `RawPaperStore`, `PrepareJobRepository`도 같은 규칙을 따른다.

**트레이드오프** — 스키마가 없는 DB에서 웹을 띄우면 첫 요청이 테이블 부재로 실패한다. 대신 요청 경로의 DDL 잠금과
테이블 삭제 위험이 사라진다. 버전 관리형 마이그레이션 도구(Alembic 등)는 도입하지 않았고, `ensure_schema()`가
`IF NOT EXISTS`/`ADD COLUMN IF NOT EXISTS`로 멱등하게 올린다.

**eval 영향** — `test_paper_repository_sql.py`의 `test_constructor_runs_no_ddl`,
`test_ensure_schema_is_explicit_and_never_drops_tables`, `test_prepare_jobs.py`의 `test_constructor_runs_no_ddl`,
`test_prepare_worker.py`의 `test_main_ensures_schema_once_at_startup`, `test_prepare_refresh.py`의
`test_enrich_does_not_run_ddl_on_constructed_repository`. 통합 테스트 `test_retrieval_pg.py`의
`test_ensure_schema_upgrades_legacy_tables`가 기존 테이블 위에서 멱등 업그레이드를 확인한다.

**알려진 한계** — 컬럼 이름 변경이나 타입 변경처럼 `IF NOT EXISTS`로 표현되지 않는 변경은 `ensure_schema()`가 다루지
못한다. 되돌리기(downgrade) 경로도 없다.

**트러블슈팅** — 에이전트 도구 호출마다 DDL과 DROP TABLE 실행

- 증상: 에이전트 도구를 부를 때마다 PostgreSQL에 DDL 약 15개가 실행되고 `paper_ai_summaries` 테이블이 삭제됐다.
- 원인: 스키마 생성 코드가 `PaperRepository.__init__`에 있었고, 도구가 호출마다 리포지토리를 새로 만들었다.
- 확인 방법: 기준선 `paper_repository.py`의 생성자에서 CREATE·ALTER·DROP 문을 세고, 도구 코드의 생성 위치를 확인했다.
- 해결: 생성자에서 DDL을 제거하고 `ensure_schema()`와 `scripts/migrate_schema.py`로 옮겼다(dc0981d).
  `test_constructor_runs_no_ddl`, `test_ensure_schema_is_explicit_and_never_drops_tables`가 통과한다.
- 재발 방지: `test_constructor_runs_no_ddl`은 `psycopg2.connect`를 호출 즉시 실패하게 바꾼 상태에서 생성자를 부른다.
  CLAUDE.md에 "요청 경로에서 DDL 금지"를 적었다.
