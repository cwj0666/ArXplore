**결정과 근거** — 감사에서 프론트엔드 결함 다섯 가지를 고쳤다(dc0981d). (1) 로그인 후 돌아갈 경로 `next`를 검증 없이 써서
외부 사이트로 이동할 수 있었다. `safeRedirect.ts`로 같은 origin 경로만 허용했다. (2) 한글 IME 조합 중 Enter가 조합 확정과
전송을 모두 일으켜 메시지가 두 번 나갔다. `keyboard.ts`의 `isImeComposing`이 조합 중(`isComposing` 또는 keyCode 229)이면 전송하지 않는다. (3) 스트림 요청의 non-OK
응답을 확인하지 않아 오류가 화면에 드러나지 않았다. `response.ok`를 확인해 오류로 표시한다. (4) 오류 문구가 대화 이력에
들어가 다음 요청의 LLM 입력이 됐다. 실패한 턴은 이력에서 뺀다. (5) `AppHeader`가 조건부 return 뒤에 훅을 불러 React 훅
순서 규칙을 어겼다.

**트레이드오프** — 프론트엔드에는 단위 테스트 러너가 없어 이 수정들은 타입 검사·빌드와 리뷰로만 검증했다. 테스트 러너
도입은 범위 밖으로 미뤘다. 이후 로그인 기능을 없애면서(phase-4, e8b57f9) `safeRedirect.ts`와 로그인 화면은 삭제됐다.

**eval 영향** — CI frontend 잡(`npm run typecheck`, `npm run build`). 실패 턴을 이력에서 빼는 규칙은 서버 쪽에서도
`test_api_views.py`의 `test_current_question_echoed_in_history_is_dropped`와 생성 평가의 대화 케이스(conversation 7건)가
확인한다.

**알려진 한계** — 브라우저 동작(IME, 리다이렉트)을 자동으로 확인하는 테스트가 없다.

**트러블슈팅** — 로그인 뒤 이동 경로로 외부 사이트 이동

- 증상: 로그인 페이지의 `next` 파라미터로 외부 도메인으로 이동할 수 있었다. 첫 수정 뒤에도 `/a/..//evil.com` 입력이
  검사를 통과했다.
- 원인: 기준선은 `next`를 검사하지 않았다. 첫 수정(dc0981d)은 파싱한 URL의 origin만 비교했는데, `/a/..//evil.com`은 같은
  origin으로 파싱되면서 경로가 `//evil.com`으로 정규화되고, 이 경로로 이동하면 프로토콜 상대 URL이 되어 외부로 나간다.
- 확인 방법: 1차 리뷰(산타 방식)에서 이 입력이 지적됐고, 정규화된 pathname이 `//evil.com`이 되는 것을 확인했다.
- 해결: origin 비교에 더해 정규화된 pathname이 `//`로 시작하거나 백슬래시를 포함하는 경우를 퍼센트 디코딩 뒤에도
  거부했다(f229c59). 프론트엔드 테스트 러너가 없어 CI frontend 잡의 타입 검사·빌드와 리뷰 재확인으로 검증했다.
- 재발 방지: 로그인과 `next` 파라미터 자체를 phase-4에서 없앴다(e8b57f9). 현재 코드에는 이 리다이렉트 경로가 없다.
