**결정과 근거** — 기준선 README의 기능·구성 설명 중 코드와 맞지 않는 부분이 있어, 코드를 기준으로 README를 다시
썼다(8d20944). 팀 프로젝트라는 성격과 담당 범위, 실제 기능, 검색 계층 현황을 적고, 평가 표는 값 없이 "측정
예정"으로 두어 측정 전에는 수치를 쓰지 않는다는 규칙을 README 안에 명시했다. `.env.example`은 당시 런타임이 읽는 변수 57개를
필수·선택으로 나눠 기본값과 함께 적었다. 원격 서버(PostgreSQL, Airflow)에 접근할 수 없는 사람도 웹을 띄울 수 있도록
`local-db` compose 프로필(pgvector 이미지, `127.0.0.1`에만 공개)을 더했다.

**트레이드오프** — README를 코드에 맞추면서 팀 시절 문서(`docs/management/ROLES.md`, `TEAM_SETUP.md`)는 "팀 프로젝트 당시
문서"로 표시만 하고 고치지 않았다. 역사 기록과 현재 동작 설명을 섞지 않기 위해서다. `local-db`는 수집 DAG가 없으므로 빈
DB로 시작한다.

**eval 영향** — 평가 표를 "측정 예정"으로 두는 규칙 때문에, 검색·생성 수치는 `eval/results/*.md`에 남은 실행 결과로만
채운다. 결과 파일은 실행 시각·커밋·질의셋 sha256·코퍼스 크기를 머리에 적는다.

**알려진 한계** — 문서와 코드의 일치는 리뷰로만 확인하고 자동 검사는 없다. 예외는 평가 케이스 수로,
`test_eval_cases.py`의 `test_readme_lists_the_actual_counts`가 `eval/README.md`의 케이스 수를 실제 파일과 대조한다.

**트러블슈팅** — 해당 없음
