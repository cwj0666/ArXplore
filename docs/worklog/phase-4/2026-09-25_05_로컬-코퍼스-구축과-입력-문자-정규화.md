---
title: 로컬 코퍼스 구축과 입력 문자 정규화
date: 2026-09-25
area: [eval, pipeline]
decision: HF Daily Papers 14일치로 275편·청크 15,897개·임베딩 14,125개의 로컬 코퍼스를 만들어 평가 기반으로 쓰고, 구축 중 드러난 서로게이트 문자와 NUL 문자 결함을 파싱 직후와 검색·API 진입점에서 정규화해 막는다
---

**결정과 근거** — 원격 서버 DB 없이 평가하려고 작업 공간의 PostgreSQL 16.2 + pgvector 0.6.2에 로컬 코퍼스를 만들었다. HF
Daily Papers 14일치에서 375건을 가져와 논문 275편을 저장했고, 청크 15,897개(body 12,659, references 1,772, table_like
1,036, front_matter 306, figure_caption 86, appendix 37, toc 1), 임베딩 14,125개(text-embedding-3-large, 1536차원)를 만들었다.
GPU 파서 없이 pypdf로 처리해 본문 source는 모두 `pdf`다. 구축과 첫 평가 실행에서 두 결함이 나왔고, 해당 문자를 경계에서
지우는 쪽으로 고쳤다(24c067f, 5f9c4cd, 0217493).

**트레이드오프** — 서로게이트 문자와 제어 문자를 지우면 원문과 저장본이 1:1로 대응하지 않는다. 대체 문자(U+FFFD)로 바꾸는
대안은 검색 토큰을 새로 만들기 때문에 지우는 쪽을 택했다. 평가 코퍼스가 14일치 275편이라 운영 규모에서의 지연·인덱스 효과는
이 코퍼스로 말할 수 없다.

**eval 영향** — 검색·생성 평가 결과 파일 머리의 코퍼스 줄(papers 275, chunks 15897, embeddings 14125, 본문 source pdf 275)이
이 구축의 결과다. 테스트: `test_prepare_pipeline.py`의 `test_surrogate_characters_are_stripped_before_hashing_and_saving`,
`test_retrieval_filters.py`의 `test_strips_control_characters_and_collapses_whitespace`,
`test_nul_query_reaches_backends_without_control_characters`, `test_query_empty_after_stripping_skips_every_backend`,
`test_detail_chat.py`의 `test_control_characters_are_removed_from_chat_messages`.

**알려진 한계** — `layout_pdf` 경로(HURIDOCS)로 만든 청크는 이 코퍼스에 없다. 최종 검색 실행(20260925-225658, 5f9c4cd)은
ablation 경로 정규화(0217493) 전에 돌아서 `lexical_nodiv`, `hybrid_nodiv`, `lexical_nofilter`가 제어 문자 케이스 1건을
오류로 빼고 114건으로 집계됐다.

**트러블슈팅** — 서로게이트 문자로 본문 해시 계산 실패

- 증상: 코퍼스 구축 중 4개 날짜의 prepare가 `compute_fulltext_content_hash`에서 `UnicodeEncodeError`로 실패했다.
- 원인: pypdf가 추출한 텍스트에 짝이 없는 서로게이트 코드포인트(U+D800~U+DFFF)가 섞여 있었고, 해시를 위해 UTF-8로
  인코딩하는 순간 실패했다.
- 확인 방법: 실패한 날짜들의 예외 위치가 모두 해시 계산의 인코딩이었고, 해당 본문에서 서로게이트 문자를 확인했다.
- 해결: 파싱 직후 본문 텍스트와 섹션 제목·본문에서 서로게이트를 지운다(`strip_surrogates`, 24c067f).
  `test_surrogate_characters_are_stripped_before_hashing_and_saving`이 통과하고, 재처리 뒤 275편 모두 청크를 가진다(결과
  파일의 "청크 보유 275").
- 재발 방지: 해시와 저장 전에 같은 정규화를 거치는 것을 단위 테스트가 확인한다. raw 저장 쪽 NUL은
  `test_nul_characters_are_stored_without_error`가 따로 지킨다.

사례 2 — NUL 문자가 든 질의로 검색이 ValueError

- 증상: 제어 문자가 섞인 안전 케이스(`sf-control-chars-mixed`)가 검색에서
  `ValueError: A string literal cannot contain NUL (0x00) characters.`로 실패했다.
- 원인: psycopg2는 NUL이 든 문자열 파라미터를 거부하는데, API와 retriever 진입점이 제어 문자를 지우지 않았다.
- 확인 방법: 검색 평가 질의별 CSV의 `error` 열. 24c067f 시점 실행(`20260925-222321.csv`)의 lexical 1건, 5f9c4cd 시점
  실행(`20260925-225658.csv`)의 ablation 3개가 같은 케이스·같은 오류였다.
- 해결: API 입력에서 줄바꿈·탭을 뺀 제어 문자를 지우고(`strip_control_characters`, 24c067f), retriever 진입점의
  `normalize_search_query`가 제어 문자를 지우고 빈 질의면 DB를 부르지 않게 했으며(5f9c4cd), 평가 ablation 경로도 같은
  정규화를 거치게 했다(0217493). 위 테스트들이 통과하고, 제품 경로(lexical·vector·hybrid)는 최종 실행에서 오류 0건이다.
- 재발 방지: 제어 문자 케이스가 평가 카탈로그 safety 관점에 상주하고, 오류는 결과 표의 `errors` 열에 드러난다.
