---
title: HURIDOCS 코퍼스 재구축과 수식·표 파싱 끄기
date: 2026-09-26
area: [pipeline, infra]
decision: 첫 실측 코퍼스(pypdf 275편)를 GPU 파드의 HURIDOCS로 다시 만들되, 수식·표 변환이 CPU에 묶여 논문당 수 분이 걸리므로 이번 재구축은 `LAYOUT_PARSER_PARSE_TABLES_AND_MATH=false`(운영 기본값과 다름)와 prepare worker 1개 순차 실행으로 처리한다
---

**결정과 근거** — 첫 실측(`20260925-225658.md`)은 본문 source가 모두 pypdf라 레이아웃 파서의 효과를 말할 수 없었다. 같은
14일치(HF Daily Papers 2026-09-11 ~ 09-24)를 RunPod GPU 파드(RTX 4000 Ada 20GB, Docker 없음)에서 HURIDOCS v0.0.31을 네이티브로
빌드해 다시 처리했다. 수집은 날짜별 `run_collect_papers(enqueue_prepare=True)`로 했다. `run_backfill_collect_papers`는 내부에서
`enqueue_prepare=False`라 `prepare_jobs`에 잡이 들어가지 않기 때문이다. raw 375행에서 고유 논문 275편이 나왔고, 첫 실측 코퍼스와
같은 수이며 평가 질의셋의 정답 논문 57편이 모두 들어 있었다.

수식·표 파싱을 켠 상태(운영 기본값)에서 28쪽 논문(수식 128개, 표 3개) 하나를 파드에서 단독으로 cProfile로 재니 195초였다.
pix2tex 수식 인식 83초(수식당 0.65초), RapidOCR 표 텍스트 검출 47초(표 3개), `torch.save` 20초, multiprocessing
`close_fds` 23초가 들었고 VGT 레이아웃 추론은 11초였다. 같은 논문을 수식·표 파싱 없이 돌리면 19초다. 병렬로 줄이려고 인스턴스
3개와 worker 3개를 돌리자 43쪽 논문 하나에서 14분 동안 한 편도 끝나지 않았다. 파드의 cgroup CPU 쿼터가 약 15코어라 CPU에
묶인 단계가 서로 밀어냈다. 날짜 잡이 같은 논문을 공유해 세 worker가 같은 논문을 동시에 파싱하고 있었다.

그래서 이번 재구축은 수식·표 파싱을 끄고(worker 프로세스 환경변수로만 지정, `.env`와 `src/`는 그대로) HURIDOCS 인스턴스
1개와 prepare worker 1개로 순차 처리했다. 14개 날짜 잡이 실패 없이 끝났고(08:10:34 → 10:27:48 UTC, 8,234초, raw 1행당 약
22초), 본문 source는 275편 모두 `layout_pdf`, 청크 16,011개, 임베딩 13,329개다(`content_role=references` 청크 2,682개는
설계상 임베딩하지 않는다). 수치는 `eval/results/20260926-103105.md` 머리말과 같다.

**트레이드오프** — 수식은 LaTeX 대신 pdftohtml 텍스트, 표는 HTML 대신 텍스트로 들어간다. 이번 재측정의 목적은 pypdf 대비
레이아웃 파싱(섹션·`content_role`·읽기 순서)의 효과라서 받아들였다. 대신 운영 기본값과 다른 코퍼스의 수치이고, README와
결과 해석에 조건을 적었다. 수식·표를 켠 채 RapidOCR 스레드만 제한하는 안은 편당 1~2.5분 × 약 375회로 추정돼 택하지 않았다.
worker 병렬화는 아래 트러블슈팅의 고정 경로 충돌과 날짜 간 중복 때문에 포기했다. 파드의 HURIDOCS 사본에는 pix2tex GPU
패치를 남겼지만 이번 실행에서는 수식 파싱을 쓰지 않았다.

**eval 영향** — 결과 파일 머리말의 "본문 source: layout_pdf 275"와 코퍼스 줄(chunks 16011, embeddings 13329)이 이 코퍼스를
가리킨다. `content_role` 분포는 첫 실측 대비 references 1,772 → 2,682, figure_caption 86 → 157, appendix 37 → 65,
body 12,659 → 11,962, table_like 1,036 → 832, front_matter 306 → 306, toc 1 → 7로 바뀌었다. 역할 판정 코드
(`src/integrations/pdf_parser/section_roles.py`)는 그사이 바뀌지 않았으므로 순수한 파서 차이다. 해석은 같은 날
"layout_pdf 재측정 결과 해석" 항목에 있다.

**알려진 한계** — 수식·표 파싱을 켠 운영 조건의 검색·생성 수치는 없다. 인라인 임베딩은 논문당 200청크(`--embed-max-chunks`)
상한이라 긴 논문은 마지막 잡 뒤 backlog 임베딩으로 채워졌다(최종 누락 0, references 제외). 파드의 HURIDOCS 사본 수정과
인스턴스 분리는 저장소에 들어 있지 않다.

**트러블슈팅** — pix2tex가 CPU에서 돌고 요청마다 모델을 다시 불러옴

- 증상: 수식·표 파싱을 켠 28쪽 논문 하나가 11분이 넘도록 끝나지 않았고, GPU 사용률은 0%, 서버 프로세스 CPU는 약 1,650%였다.
- 원인: HURIDOCS `convert_formula_to_latex.py`가 `LatexOCR()`를 인자 없이 만들어 pix2tex 기본값 `no_cuda=True`(CPU)를 썼고,
  요청마다 모델을 새로 불러왔다.
- 확인 방법: pix2tex `cli.py`의 기본 인자(`'no_cuda': True`)와 서버 로그의 모델 가중치 다운로드·로드를 확인했다.
- 해결: 파드의 HURIDOCS 사본만 `no_cuda=False` + 프로세스당 1회 로드로 고쳐 같은 논문이 194초가 됐다. 이후 cProfile로 남은
  시간(pix2tex 83초, RapidOCR 47초 등)도 CPU에 묶여 있음을 확인하고 이번 재구축은 수식·표 파싱을 껐다(19초).
- 재발 방지: README "알려진 한계와 로드맵"에 수식·표 파싱 조건과 소요 시간을 적었다. HURIDOCS를 Docker 이미지 대신 직접
  빌드할 때 이 기본값을 확인해야 한다.

사례 2 — HURIDOCS 동시 요청이 고정 경로를 덮어써 pypdf로 폴백

- 증상: gunicorn 워커 3개와 prepare worker 3개로 돌리자 파서가 404(`No xml file`)와 422(`KeyError: 'font'`)를 돌려주고, 3편이
  `source=pdf`로 저장됐다.
- 원인: `pdf_features`가 pdftohtml 결과를 `/tmp/pdf_etree.xml` 고정 경로에 쓰고, HURIDOCS가 루트 아래 `images/`,
  `jsons/test.json`, `model_output_doclaynet/`을 요청마다 만들고 지운다. 동시 요청이 서로의 파일을 덮어쓰거나 지웠다.
- 확인 방법: 서버 로그 트레이스백(`PdfFeatures.from_poppler_etree`의 `KeyError: 'font'`)과 `catch_exceptions`의
  `FileNotFoundError → 404` 매핑, 각 인스턴스 루트에 생긴 작업 디렉터리를 확인했다.
- 해결: 인스턴스마다 루트(원본 + `src` 복사본·`models` 심링크)와 `TMPDIR`을 나누고 worker 하나가 인스턴스 하나만 쓰게 하자
  같은 논문 3편을 동시에 파싱해도 결과가 바이트 단위로 같았다. 다만 날짜 잡 간 중복 때문에 최종 실행은 worker 1개로 했다.
  pypdf로 폴백됐던 3편은 source 순위(`layout_pdf > pdf`) 덕분에 `--force` 없이 `layout_pdf`로 덮였다.
- 재발 방지: 운영 compose는 prepare worker 1개가 HURIDOCS 1개에 순차로 요청하는 구조라 이 문제가 없다. 병렬화할 때는
  인스턴스를 분리해야 한다는 점을 이 항목에 남긴다.

사례 3 — 파싱 전 중복 건너뛰기가 없어 같은 논문을 여러 번 파싱

- 증상: 고유 논문 275편에 raw 375행을 모두 파싱했고, 09-12·09-13 날짜 잡(각 26편)은 약 530초씩 파싱만 하고 저장할 것이 없었다.
  날짜 병렬 실행에서는 세 worker가 같은 43쪽 논문을 동시에 파싱했다.
- 원인: `prepare_single_paper`가 PDF를 파싱한 뒤에야 source 순위와 `content_hash`로 unchanged를 판정한다. HF Daily Papers는
  주말(09-12, 09-13)에 금요일 목록을 그대로 반복한다.
- 확인 방법: 날짜 잡의 `claimed_at`·`finished_at`과 raw `fetched_count`, 파서 임시 디렉터리의 동일 md5 PDF를 대조했다.
- 해결: 이번 실행에서는 코드를 바꾸지 않고 중복 파싱(약 100회)을 감수했다.
- 재발 방지: README 로드맵에 "파싱 전 중복 건너뛰기 없음"을 개선 후보로 올렸다(기존 본문이 `layout_pdf`이고 청크가 있으면
  `force`가 아닐 때 파싱을 건너뛰는 안).
