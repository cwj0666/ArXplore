**결정과 근거** — 68dab7b 기준으로 코드 전체를 읽기 전용으로 분석했다(분석과 계획은 저장소 밖
`~/portfolio/02_projects/arxplore/reports/refactor/`, 계획은 `06_plan.md`). 다시 짜기로 한 근거는 다음과 같다.
- Django는 ORM·admin·auth·세션·템플릿을 하나도 쓰지 않고 라우팅·CSRF·캐시·Paginator만 쓴다.
- SSE가 동기 WSGI(gunicorn gthread 4×8) 위에서 스트림마다 스레드를 붙잡는다.
- Airflow는 DAG 3개, 하루 몇 번의 HTTP 호출에 컨테이너 4개와 시크릿 3종을 쓴다.
- 최상위 패키지 이름이 `src`이고 `sys.path` 조작이 12곳이다.
- 에이전트가 LangGraph 1.0에서 deprecated된 `create_react_agent`를 쓴다.
- 단위 테스트 다수가 SQL 문자열과 private 함수에 묶여 있고, eval 하네스가 retriever private 메서드 7개에 묶여 있다.

사용자 결정(2026-09-29):
- 백엔드는 FastAPI, 스케줄러는 경량 스케줄러로 바꾼다.
- 알려진 버그는 리라이트하면서 고친다.
- 평가 하네스와 연구 코드는 제품 저장소에 둔다.
- 로컬 환경은 WSL Docker로 한다.
- 분석에서 새로 찾은 수정 제안 13개를 모두 넣는다.
- 기존 코퍼스를 재파싱한다.
- 작업은 `refactor/v2`(68dab7b에서 분기)에서만 하고 push하지 않는다. `develop/portfolio-2026-09`와 fork 원격은 그대로 둔다.

진행 방식:
1. 모듈을 먼저 골든과 같게 옮긴다.
2. 그 위에 수정 커밋을 하나씩 얹는다. 골든 차이는 계획 6절의 수정 ID가 붙은 커밋에서만 허용한다.
3. 안전망으로 가짜 OpenAI 서버를 만든다. 옛 구현과 새 구현 모두 `OPENAI_BASE_URL`만 바꿔 붙을 수 있어, 내부를 patch하지 않고 같은 시나리오를 양쪽에 돌린다.
4. 골든은 6종이다: 검색 순위(G1), 청크(G2), 파서(G3), LLM 요청(G4), HTTP·SSE(G5), 화면(G6).
5. 코드에 주석과 docstring을 쓰지 않는다. LLM에 넘어가는 도구 설명은 `@tool(description=...)`처럼 명시적 인자로 둔다.

목표 스택은 계획 2절이다. 버전 해석에서 두 가지가 조정됐다.
- ragas 0.4.3이 langchain을 1.3.x, openai를 3.3으로 묶는다.
- typescript-eslint 8.71이 TypeScript `<6.1`만 지원해 TypeScript는 6.0으로 둔다.

**트레이드오프** — 고려한 대안과 비용은 다음과 같다.
- Django 5.2 LTS + ASGI 전환: 변경은 작지만 쓰지 않는 프레임워크를 계속 끌고 간다. FastAPI는 CSRF(bootstrap 쿠키와 헤더 대조, Origin 검사), 분 단위 rate limit, `Paginator.get_page` 의미를 직접 재현해야 한다.
- Airflow 유지: 실행 이력 UI와 수동 트리거 params를 잃는 대신 CLI `arxplore run`과 `scheduler_runs` 테이블로 대신한다.
- 1차 보존 후 2차 수정(분석 단계의 권장): 사용자가 리라이트 중 수정을 골랐다. 대신 동등 이식과 수정을 커밋 단위로 분리해 차이를 추적한다.
- eval 결과 파일의 저장소 밖 이전: 하지 않는다.
- 지불할 비용
  - 재임베딩(약 600만 토큰)과 재파싱(GPU 1.5시간 이상)
  - 청크 id가 바뀌어 G1·G2와 청크 합성 질의 정답을 다시 만들어야 함
  - ragas 때문에 langchain을 한 단계 낮춰 씀

**eval 영향** — 새로 생기는 측정 지점은 다음과 같다.
- `tests/golden`의 G1~G6
- 양쪽 구현에 같은 시나리오를 돌리는 `tests/contract`
- 수정 전 코드로 `eval/results/20260929-005408`의 검색 지표 재현
- F01~F04 코퍼스 전환 뒤 검색 재측정. 생성 평가 재수집은 승인 뒤에 한다.

`tests/unit/fixtures/hybrid_fusion_golden.json`(LEGACY 규칙)은 연구용 융합과 함께 `arxplore_eval`로 옮긴다.

**알려진 한계** — 골든과 계약 테스트가 보장하는 범위에는 다음 한계가 있다.
- 골든은 로컬 덤프 코퍼스에 묶여 있다.
- HURIDOCS segment에서 sections로 가는 단계는 수집한 원본 응답 표본으로만 검증한다.
- 가짜 OpenAI 서버는 요청 동등성만 보장하고 답변 품질은 보지 않는다.
- 화면 동등성은 스크린샷 허용 오차 안에서만 본다.
- F01~F04는 청커 수정, 정제 수정, 재파싱이 한꺼번에 반영되므로 전후 검색 지표 차이를 한 원인으로 읽을 수 없다.

**트러블슈팅** — 커밋된 질의셋과 결과가 쓴 질의셋 불일치

- 증상: 커밋된 `eval/queries.jsonl`의 sha256이 82e4a51cce90으로, EVALUATION.md와 `eval/results/20260929-005408.md`가 쓴 fe0cce78a89b와 달랐다.
- 원인: 2026-09-28 코퍼스 재구축 뒤 청크 합성 질의 11건의 정답 청크 id를 재매핑한 파일을 저장소에 넣지 않았다(2026-09-28_02, 2026-09-29_03 참고). 옛 id도 새 DB에 행으로 존재해 preflight를 통과하므로 청크 단위 지표만 조용히 틀어진다.
- 확인 방법: 저장소 밖 사본(`data/queries_remapped_trackA_20260928.jsonl`)과 비교했다. 순서와 id는 같고 `relevant_chunk_ids` 11건만 달랐다.
- 해결: 1b8853b에서 `queries.jsonl`과 `queries.generated.jsonl`의 11건을 바꿨다. `queries.jsonl`이 generated + cases를 이어 붙인 결과와 같은지 확인했고, 단위 테스트 1,145개가 통과했다.
- 재발 방지: P7에서 두 원본 파일을 이어 붙인 결과와 `queries.jsonl`이 같은지 검사하는 테스트를 넣는다.
