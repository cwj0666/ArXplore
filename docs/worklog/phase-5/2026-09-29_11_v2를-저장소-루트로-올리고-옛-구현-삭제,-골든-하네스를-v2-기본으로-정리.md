**결정과 근거** — 계획 3절의 목표 구조로 전환하는 마지막 단계다. 각 커밋 시점에 테스트가 깨지지 않도록 옛 구현에 기대던
것부터 떼고, 그다음 지우고, 마지막에 옮겼다.

1. 골든 하네스를 옛 구현에서 떼기
   - G6(946a46e): v2 캡처가 새 프론트를 옛 Django에 붙이고 있었다. 이제 하네스 환경의 `arxplore migrate`와
     `arxplore api`(`SERVE_FRONTEND_DIST=true`)를 `.env`가 없는 임시 폴더에서 띄워, 빌드와 API를 한 주소에서 낸다. 픽셀 비교에
     쓰는 numpy·pillow는 dev 그룹에 넣었다(a9d01be). 백엔드가 바뀌며 7개 화면이 달라졌고 원인은 모두 G5에 기록된 수정이다:
     목록 두 화면은 F32(같은 게시일 안에서 arxiv_id 순), 상세 다섯 화면은 F20(`3.5%`). 두 번 캡처가 바이트 단위로 같아 변형으로
     저장했다(`g6_ui.v2.diff.md`).
   - 0190db9: `GOLDEN_IMPL` 기본값을 v2로 바꾸고 옛 코드를 import하던 `adapters/legacy.py`, Django 환경, psycopg2 폴백, G5 바이트
     비교 규칙, G6 옛 캡처를 지웠다. 캡처 스크립트는 기본으로 `<이름>.v2.json.gz`를 써서 원본을 덮지 않는다. G1
     `embed --dry-run`은 실제 API를 부르기 전에 멈추고 입력이 표에 있는지 본다. v2 드라이런은 입력 555개(고유 138개)를 보냈고
     모두 `g1_query_embeddings.json.gz`에 있었다.
   - b947162: G1 질의셋을 옛 `eval.dataset` 대신 `arxplore_eval.dataset`으로 읽는다. 142개 질의의 id, 문장, 검색 대상 여부,
     모드, 상세 챗 논문이 옛 로더와 같았다.
2. 옛 구현 삭제(d5d0db9): backend, `src/{core,integrations,pipeline,shared}`, dags, 옛 frontend, 옛 tests, `eval/*.py`,
   `scripts/eval_*.py`와 옛 스크립트 4개, requirements, 옛 compose와 Dockerfile. `v2/scripts/compare_schema.py`,
   `diff_repositories.py`는 옛 구현을 import하는 비교 도구라 함께 지웠고 결과는 03번 항목에 있다.
3. 루트로 이동(8dc2463): 파일 386개를 이름 바꾸기로 옮겼다(`git log --follow`가 v2 이력을 따라간다). 저장소 루트를
   `parents[4]`로 계산하던 테스트 6곳을 고치고, `.gitignore`를 합쳤다. ruff는 루트와 `src`에서 first-party를 찾아
   `tests/golden`, `tests/fakes`, `scripts`도 v2 규칙으로 검사한다. pytest에 `golden` 마커를 등록했다.
4. 정리: CI python 잡이 골든 DB 없이 도는 가짜 서버·골든 하네스 테스트를 돌리고(31f1a77), `scripts/worklog.py`의 docstring을
   지웠다(bd2f568). `retrieval.vector`가 `hnsw.ef_search` 설정문과 적용 규칙을 `hnsw_ef_search_statement`로 내고
   `arxplore_eval.explain`의 복제를 지웠다(aa7226e).
5. 문서: README, ARCHITECTURE, SETUP, EVALUATION, `eval/README.md`, AGENTS, CLAUDE를 새 구조로 다시 썼다. `docs/management`의 팀
   시절 문서 3개는 `docs/archive/team-2026-04/`로 옮기고 현재 문서에서 링크하지 않는다.

전환 뒤 검증(루트 `.venv`, Python 3.14)
- `uv sync --frozen`, ruff check·format, mypy(143 파일) 통과. 단위 1,690, 통합 265(골든 DB를 주면 lexical 재현 1개 추가), 가짜
  서버·골든 878 통과(HURIDOCS 실제 파서 비교 10개는 파서가 없어 건너뜀). 골든은 G1 351(정확 검색도 351), G2 278, G3 pypdf 40,
  G3-layout 재생 20, G5 121, G5 규칙 19, G6 11이다.
- 프론트: `npm ci`, lint, typecheck, test 69, build, `check:api` 통과. `worklog.py check` 통과.
- compose: 두 파일 `config -q` 통과(서버 파일은 `TAILSCALE_SERVER_IP`를 준 경우). 커밋된 트리를 내보낸 폴더에서 가짜 `.env`로
  app·web·parser 이미지를 빌드하고(app 414MB, web 93.6MB), 프로젝트 `arxplore-cutover-smoke`로 `arxplore_tpl` 복사본에
  0001~0006을 적용한 뒤 api·web을 띄웠다. `/`, `/papers/list.json`(275편), 상세 챗·어시스턴트 SSE, JSON 챗, CSRF 403 등 17개
  확인이 통과했고 LLM 요청은 모두 가짜 서버로 갔다. 확인 뒤 컨테이너, 볼륨, 이미지, DB 복사본을 지웠다.

**트레이드오프** — 삭제와 이동을 한 커밋에 넣으면 같은 경로(`frontend/`, `pyproject.toml` 등)가 "수정"으로 보여 v2 이력이
끊긴다. 그래서 옛 파일을 먼저 지우는 커밋을 따로 두었고, 그 사이 커밋에서는 v2 테스트를 `v2/`에서 돌린다.
- 원본 골든을 다시 캡처할 수 없게 됐다. 옛 구현이 없으므로 원본은 기준선으로만 남고, 이후 차이는 모두 v2 변형과 diff 문서로
  기록한다.
- G6은 vite preview 대신 FastAPI의 SPA 서빙으로 캡처한다. 운영의 nginx 서빙과는 다른 경로지만 두 경로 모두 같은
  `frontend/dist`를 내고, nginx 규칙은 스모크로 따로 확인한다.
- numpy·pillow를 dev 그룹에 넣어 CI 설치가 조금 커졌다. 대신 골든 하네스가 pytest 수집 단계에서 깨지지 않는다.
- 통합 테스트 변수 `V2_TEST_DATABASE_URL`, `V2_TEST_REQUIRE_DB`와 DB 이름 규칙 `v2_test*`는 바꾸지 않았다. 이름에 v2가 남지만
  작업자 스크립트와 CI, 기존 테스트 DB를 그대로 쓸 수 있다.
- 실패한 잡만 다시 여는 옛 `requeue_failed_prepare_jobs.py`를 지웠다. 저장소 함수 `jobs.requeue_failed`는 있지만 명령이 없어,
  지금은 날짜 범위의 잡을 다시 여는 `arxplore run reparse --no-force`로 대신한다. done 잡도 다시 열린다.

**eval 영향** — CI python 잡에 `pytest tests/fakes tests/golden` 단계가 생겼다. 골든 DB 없이 101개가 돌고 787개가 건너뛴다
(가짜 서버, 골든 저장소·하네스, G5 비교 규칙, G3 HURIDOCS 응답 재생, 원본 G3·G6 매니페스트).
- G6 변형: `g6_ui.v2/`에 7개 화면(21개 파일)이 새로 생기거나 바뀌었다.
- `capture_g1_retrieval embed --dry-run`: 저장된 질의 임베딩 표로 충분한지 비용 없이 확인한다.
- `arxplore-eval explain`이 제품과 같은 `hnsw_ef_search_statement`를 쓴다(골든 코퍼스에서 hybrid 벡터 채널 `hnsw.ef_search 600`).

**알려진 한계** — eval 그룹은 설치되지만(`uv sync --frozen --group eval`, scikit-network 0.33.5를 약 1분 동안 소스 빌드)
ragas 0.4.3이 lock의 langchain-community 0.4.2에 없는 `langchain_community.chat_models.vertexai`를 import해 `import ragas`가
실패한다. 그래서 RAGAS 채점을 돌릴 수 없고, 하네스는 이 오류를 "ragas가 설치되어 있지 않습니다"로 보고한다. langchain-community
0.4.1 휠에는 이 모듈이 있다. ragas를 부르는 단위 테스트는 없고, eval 단위 592개는 그룹 설치 전후로 같다.
- 코퍼스 전환(재파싱, 재청킹, 재임베딩)과 검색·생성 평가 재측정은 아직 없다. 문서의 수치는 전환 전 코퍼스의 값이다.
- HURIDOCS 실제 파서 비교(G3-layout live 10개)는 이 단계에서 돌리지 않았다. 응답 재생 20개만 돌았다.
- `.gitleaks.toml`과 `.gitleaksignore`에는 예외 사유를 적은 주석이 남아 있다.
- F38(analyze·summary의 버전 붙은 id 조회)은 승인 대기라 반영하지 않았다.

**트러블슈팅** — 가짜 서버의 스트림 중단 테스트가 새 환경에서 실패

- 증상: 골든 하네스를 프로젝트 환경(Python 3.14)으로 돌리자 `tests/fakes/test_openai_server.py::test_a_reply_can_abort_the_stream_after_some_events`가
  실패했다. 옛 환경(Python 3.12)에서는 통과하던 테스트다.
- 원인: openai 3.3은 httpx 대신 httpx2로 요청을 보낸다. 가짜 서버가 스트림을 끊으면 `httpx2.RemoteProtocolError`가 올라오는데,
  테스트는 `httpx.HTTPError`나 `openai.APIError`만 기다렸다.
- 확인 방법: 실패 트레이스백의 예외 모듈과 `openai` 배포본의 의존성(`Requires-Dist: httpx2`), `httpx2.RemoteProtocolError`의
  MRO를 확인했다.
- 해결: 74ed1a3에서 `httpx2.HTTPError`도 기대 예외로 받는다. 프로젝트 환경에서 가짜 서버 테스트 27개가 통과한다.
- 재발 방지: 가짜 서버와 골든 하네스 테스트가 CI python 잡에서 프로젝트 환경으로 돈다(31f1a77).
