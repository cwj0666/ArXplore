**결정과 근거** — "같은 동작"을 코드 읽기가 아니라 데이터로 확인하려고 리팩토링 전에 옛 구현의 출력을 골든으로
고정했다. 골든은 모두 옛 구현에서 두 번 이상 캡처해 바이트가 같은지 확인했다(G6은 세 번).

| ID | 대상 | 내용 | 커밋 |
| --- | --- | --- | --- |
| G1 | 검색 순위 | 평가 경로 111질의 × lexical·vector·hybrid(k=10), 제품 `retrieve_contexts` 142질의 × 3모드(hybrid, lexical, 임베딩 실패 폴백), 상세 챗 97쌍. hit마다 chunk_id, 점수 repr, 섹션, role, 문맥 sha256 | e7a663f |

- 골든 DB는 Docker `arxplore-golden-pg`다. 읽기는 `default_transaction_read_only=on` 세션으로 하고, 쓰기가 필요한 캡처는
  템플릿 `arxplore_tpl`의 `golden_*` 복사본에서 한다. 골든 테스트는 루프백 밖으로 나가는 연결을 막는다(a26c69a, 01300b8).
- 가짜 서버 `tests/fakes/openai_server.py`(8384d80)는 표준 라이브러리 `ThreadingHTTPServer`라 Python 3.12(옛)와 3.14(새)
  모두 `OPENAI_BASE_URL`, `OPENAI_API_BASE`, `ARXIV_API_BASE_URL`만 바꿔 붙는다.
  - chat completions: 스트림·비스트림, 고정 크기 조각, 도구 호출 delta, `include_usage` 사용량 청크. 기본 답은 마지막
    사용자 메시지의 sha256에서 만든 문장이고, 스트림을 중간에 끊는 응답도 낸다(562a189).
  - 임베딩은 텍스트 sha256으로 시드한 단위 벡터나 저장해 둔 표에서 돌려주고, arXiv Atom 응답도 낸다.
  - 받은 요청을 순서대로 모두 기록한다. 내부를 patch하지 않으므로 같은 시나리오를 두 구현에 그대로 돌린다.
- G5는 번들마다 `golden_*` DB 복사본과, 저장소 밖에서 깨끗한 환경으로 뜬 하위 프로세스에서 돈다. `.env`가 빈 값을
  다시 채우지 못하게 하기 위해서다. 옛 구현은 `httpx.WSGITransport`로, 새 구현은 `httpx.ASGITransport`로 부른다(7984ccf,
  0530057).
- P0에서 정한 비교 규칙
  - G4는 `stream_options`를 뺀 요청 본문을 비교한다(사례 2).
  - 요약 그래프 호출은 섹션 분류별·버킷별로 묶어 비교하고, 최종 호출이 마지막이라는 것만 순서로 본다(사례 1).
  - G1은 기본 실행과 정확 검색(`GOLDEN_EXACT_SEARCH=1`, `enable_indexscan=off`)을 모두 돌린다.
  - `.json.gz` 골든은 파일 바이트가 아니라 푼 내용으로 비교한다(사례 3).
- G5 v2 규칙(ca5af91): 새 구현의 응답은 상태 코드, content-type 미디어 타입, allow, 값을 뺀 set-cookie 속성, 허용 목록
  헤더(cache-control, x-accel-buffering, retry-after, location, 보안 헤더 4종), SSE 바이트, JSON 값, 그 밖의 본문 바이트로
  줄여 비교한다. 옛 골든 60개 시나리오는 이 규칙으로도 통과하고, `tests/golden/test_g5_rules.py`에서 일부러 만든 차이
  16종은 모두 잡힌다.

수정 절차(CLAUDE.md, `docs/architecture/AGENTS.md`)
1. 모듈을 먼저 골든과 같게 옮긴다. 이식 커밋에서는 골든 차이를 허용하지 않는다.
2. 버그는 계획 6절의 수정 ID를 단 커밋에서만 고친다. 이식하며 찾은 문제는 F32~F37로 번호를 더해 같은 절차로 고쳤다.
3. 수정이 골든을 바꾸면 원본 `<이름>.json.gz`는 옛 구현 기준으로 두고 옆에 변형 `<이름>.v2.json.gz`를 둔다.
   `GOLDEN_IMPL=v2`이면 변형이 있을 때 변형을, 없으면 원본을 읽는다(96d533d). G3는 논문별 파일로, G6는 바이트가 바뀐
   파일만 `g6_ui.v2/`에 둔다(80966b2).
4. 차이는 `tests/golden/data/*.v2.diff.md` 6개(g1_retrieval, g2_chunks, g3_pypdf, g3_layout, g5_http, g6_ui)에 수정 ID별
   규칙·수치·예시로 적는다. 각 문서 첫머리에 이식 시점의 동등성을 적었다: G1 351/351, G2 275/275편, G3 재파싱·재생
   10/10, G5·G4 60/60, G6 11개 화면.

골든이 닿지 않는 곳은 옛·새 코드를 같은 입력에 나란히 돌려 비교했다.
- 공용 문자열 정리 함수: 모든 코드 포인트와 무작위 문자열로 옛 함수와 비교하는 단위 테스트(d4ec6c1)
- 스키마와 저장소: `v2/scripts/compare_schema.py`(54a3a37), `v2/scripts/diff_repositories.py` 229단계(8ba9ec5). 03번 항목
- 파싱: 코퍼스 텍스트, 변형 텍스트, 합성 segment로 약 33만 4천 회 호출해 차이 0(95adc76)
- prepare와 worker: 같은 raw 날짜를 첫 실행, 변화 없는 재실행, 강제 재실행으로 돌려 청크 736개와 id, 임베딩 623개,
  임베딩 요청 15회, 잡 결과, worker 출력이 같았다(0aab1db, 2d626df)
- 평가 하네스: 10방식 × 111질의, 답변 235건, RAGAS 요청 계획 430건(3261077). 09번 항목

**트레이드오프** — 골든은 옛 구현의 출력이라 옛 버그도 함께 고정한다. 그래서 수정마다 골든을 바꾸는 커밋과 diff
문서 절이 따로 생긴다. 이식과 수정을 한 커밋에 섞는 것보다 느리지만, 수정 ID가 없는 커밋에서 골든이 바뀌면 의도하지
않은 동작 변화로 바로 드러난다.
- 변형 파일 방식은 원본을 덮어쓰지 않아 옛 구현 검사(`GOLDEN_IMPL=legacy`)를 계속 돌릴 수 있지만 골든을 두 벌
  관리한다. G2의 코퍼스 검사(청크 수 16,010, `paper_chunks` 대조)는 원본만 설명하므로 구현과 무관하게 원본으로 돈다
  (eacf3ae).
- 가짜 서버는 요청 동등성만 만든다. 답은 해시로 만든 문장이라 답변 품질, 실제 API의 스트림 경계와 오류 형식은 보지
  않는다.
- G1의 질의 벡터는 실제 임베딩이 아니라 가짜 서버의 결정적 벡터다. 실제 질의 임베딩 표는 `embed` 명령으로 만들도록
  해 두었고 아직 없다(e7a663f).
- 비교를 느슨하게 한 곳이 있다. G5 v2 규칙은 허용 목록 밖 헤더(vary 등)를 보지 않고, G4는 `stream_options`와 버킷 사이
  호출 순서를 보지 않는다.

**트러블슈팅** — 병렬 요약 그래프 때문에 G4 비교가 가끔 실패함

- 증상: AI 캐시 프롬프트 버전을 2로 올린 뒤(424bab6) `GOLDEN_IMPL=v2`로 G5를 돌리면 `summary:summary_cached`의 G4
  비교가 5회 중 3회 실패했다.
- 원인: 버전 1 캐시를 쓰지 않게 되면서 이 시나리오도 요약 그래프를 탔다. 그래프는 섹션 버킷을 병렬로 돌리므로 가짜
  서버에 요청이 도착하는 순서가 실행마다 바뀐다. 다른 요약 시나리오는 P0부터 호출을 버킷별로 묶어 기록했지만, 이
  시나리오는 옛 구현에서 캐시가 맞아 LLM 호출이 없었으므로 도착 순서(`sequence`) 그대로 기록하고 있었다.
- 확인 방법: 같은 코드로 G5를 반복 실행해 실패 빈도를 셌고, 기록 방식이 시나리오별 `llm_layout`에 달려 있음을
  `tests/golden/g5_http.py`에서 확인했다(`g5_http.v2.diff.md`의 F22 후속 절).
- 해결: 4f1473b에서 `summary_cached`를 `llm_layout="summary_graph"`로 기록한다. 호출을 섹션 분류별·버킷별로 묶으며, 버킷
  안의 섹션 호출은 차례로 돌아 순서가 고정된다. LLM 호출이 없으면 빈 목록을 그대로 두므로 옛 골든은 바뀌지 않았다
  (legacy 121/121). a8323a1에서 v2 변형을 다시 캡처했고 G5가 7회 연속 121개 통과했다.
- 재발 방지: 요약 그래프를 탈 수 있는 시나리오는 `Scenario(..., llm_layout="summary_graph")`로 둔다. 이 규칙과 다시
  잡은 변형의 형식은 `g5_http.v2.diff.md`에 적었다.

사례 2 — langchain-openai가 base URL 환경변수에 따라 `stream_options`를 다르게 보냄

- 증상: 가짜 서버에 붙인 옛 구현의 스트리밍 요청에는 `stream_options`가 없다. 운영처럼 base URL을 주지 않으면 같은
  호출에 `{"include_usage": true}`가 붙는다. 기록을 그대로 비교하면 운영과 같은 요청을 보내는 새 구현이 G4에서 다르게
  나온다.
- 원인: langchain-openai `ChatOpenAI`는 `stream_usage`, base URL, 클라이언트 인자가 모두 없고 `OPENAI_BASE_URL` 환경변수도
  없을 때만 `stream_usage=True`로 켠다. `OPENAI_API_BASE`는 초기화 때 `openai_api_base`로 읽혀 같은 효과를 낸다. 가짜
  서버를 붙이는 환경(`FakeOpenAIServer.environ()`)이 두 변수를 모두 주므로 사용량 요청이 꺼진다.
- 확인 방법: 루트 `.venv`(langchain-openai 1.1.0)와 `v2/.venv`(1.6.6)에서 환경변수 없이, `OPENAI_BASE_URL`만,
  `OPENAI_API_BASE`만 준 세 경우로 `ChatOpenAI`를 만들어 `stream_usage`가 각각 True, None, None임을 확인했다. 두 버전의
  초기화 코드도 같은 조건을 쓴다.
- 해결: G4는 `stream_options`를 뺀 본문을 비교한다(`tests/golden/g5_http.py`의 `_without_stream_options`, 7984ccf). 새
  구현의 모델 팩토리는 `stream_usage=True`를 명시해 base URL과 무관하게 운영과 같은 요청을 보낸다
  (`v2/src/arxplore/llm/models.py`, 4ebcb40).
- 재발 방지: `v2/tests/unit/llm/test_llm_models.py::test_created_model_uses_explicit_endpoint_key_and_usage_streaming`이 명시
  설정을 검사한다. 가짜 서버가 `include_usage`에 사용량 청크로 답하는지는
  `tests/fakes/test_openai_server.py::test_streaming_splits_content_into_fixed_pieces_and_reports_usage`가 본다.

사례 3 — 같은 골든 내용인데 gzip 바이트가 인터프리터마다 다름

- 증상: 같은 골든 내용을 두 구현의 인터프리터로 압축하면 gzip 바이트가 다르다. 옛 구현이 캡처한 원본
  (`g1_retrieval.json.gz` 등)은 루트 `.venv`(Python 3.12)에서 다시 압축하면 파일과 같고 `v2/.venv`(Python 3.14)에서는
  다르다. v2 변형 파일은 반대다.
- 원인: deflate 본문이 아니라 gzip 헤더의 OS 바이트가 다르다. Python 3.12의 `gzip.compress(..., mtime=0)`은 zlib가 만든
  헤더를 그대로 써서 OS 바이트가 3이고, 3.14의 `gzip.compress`는 헤더의 OS 바이트를 255로 덮어쓴다. 두 환경은 zlib 버전도
  다르지만 deflate 본문은 같았으므로 zlib 버전 차이는 원인이 아니었다.
- 확인 방법: 원본과 v2 변형 골든(G1·G2·G5와 G3 pypdf 일부)을 풀어 두 `.venv`에서 같은 설정(compresslevel 9, mtime 0)으로
  다시 압축하고 파일 바이트, 헤더, raw deflate(`wbits=-15`) 본문을 비교했다. 차이는 헤더의 OS 바이트 하나뿐이었고, 원인은
  두 인터프리터의 `gzip.compress` 소스에서 확인했다.
- 해결: 하네스 뼈대(a26c69a)부터 골든은 푼 내용으로 비교한다. `write_golden`은 기존 파일을 풀어 정규화 JSON이 같으면
  파일을 그대로 두고, 테스트는 `read_golden`으로 푼 값을 비교한다. G1 질의 임베딩 표의 지문도 푼 바이트의 sha256이다
