---
title: 검색 단계 공개 함수 이식과 벡터 1단계 실행 계획 확인
date: 2026-09-29
area: [retrieval, eval]
decision: PaperRetriever와 검색 SQL을 질의·lexical·vector·융합·다양성·문맥 창·모드 선택의 공개 함수로 나누되 SQL·상수·동률 규칙은 그대로 옮기고(G1 351/351), 문장은 prepare=False로 보내 호출마다 실제 값으로 계획을 세우게 한다. 그 위에 F05·F06을 얹었고, 이 코퍼스에서 제품 벡터 1단계는 HNSW가 아니라 전체 스캔으로 돈다는 것을 확인했다
---

**결정과 근거** — 옛 `PaperRetriever`는 한 클래스에 단계가 private 메서드로 묶여 있었고, 평가 하네스가 그중 7개를
직접 불렀다(01번 항목). 04e19a7에서 검색을 `arxplore.retrieval`의 공개 단계로 나눴다.
- 단계: 질의 정규화와 후보 수(`query`), lexical SQL·rerank·필터(`lexical`), `hnsw.ef_search`를 쓰는 2단계 벡터 SQL과
  rerank(`vector`), min-max convex 융합(`fusion`), 논문 다양성(`diversity`), ±1 문맥 창(`windows`), 모드 선택
  (`service.Retriever.retrieve_contexts`). 평가 하네스는 이 공개 함수만 조립한다(09번 항목).
- SQL 문장, 상수, `%.12f` 질의 벡터 리터럴, 동률 규칙(chunk_id DESC, 채널 수)은 바꾸지 않았다. 결과는
  `arxplore.domain.retrieval`의 frozen dataclass다.
- hybrid 두 채널은 각자 풀 연결을 잡고 `asyncio.gather`로 동시에 돈다. lexical 예외가 이기고 vector 채널을 취소한다.
  lexical이 성공하면 vector 예외를 그대로 낸다. `OpenAIError`만 폴백용 후보 수로 lexical을 새로 돌리는 폴백으로 이어진다.
- 연구용 융합(옛 가중 RRF 규칙, 표준 RRF, 가중 모드)은 제품에 옮기지 않고 `arxplore_eval.research_fusion`으로 보냈다.
- 질의 임베딩은 async 클라이언트 `arxplore.embedding`(64개 배치, text-embedding-3 계열에만 dimensions, 요청 키가 서버 키보다
  우선, base_url 명시)이 만들고, 요청 범위 키·모델과 검색 관찰 훅은 `arxplore.context`에 둔다.

`prepare=False`: 검색 SQL, `hnsw.ef_search` 설정문, 문맥 창 SQL은 `cursor.execute(..., prepare=False)`로 보낸다. psycopg 3는
같은 문장을 여러 번 실행하면 서버 쪽 준비 문장으로 바꾸고(기본 5회), PostgreSQL은 준비 문장을 값과 무관한 일반 계획으로
돌릴 수 있다. 옛 psycopg2는 값을 SQL 문자열에 넣어 보냈으므로 호출마다 그 값으로 계획을 세웠다. 아래 트러블슈팅처럼 벡터
1단계는 후보 수(LIMIT)에 따라 HNSW와 전체 스캔이 갈리므로, 계획이 값과 무관해지면 결과가 옛 구현과 달라질 수 있다.

동등성: 04e19a7 시점에 G1 351개 항목(평가 111, 제품 142, 상세 챗 97, 개수 검사 1)이 원본 골든과 같았고, 정확 검색
(`GOLDEN_EXACT_SEARCH=1`)에서도 351/351이었다. b32b54f부터 상세 챗 그룹은 제품 함수
`llm.paper_chat.retrieve_paper_chat_sources`로 문맥을 만들며, 첫 청크 폴백 56건을 포함해 351/351이다.

F05(507c0dd, a02125a, e1c813a): lexical SQL의 참고문헌 구조 감점(-0.08)은 `section_title ~* '<정규식>'`으로 대소문자를
무시해, 구두점 없는 소문자 로마 숫자(`iv references`)나 로마 숫자 글자로만 된 단어(`Civil References`)도 번호로 읽었다.
청크 role 규칙(`parsing.roles.is_references_section_title`)과 Python 필터·vector rerank는 그렇게 읽지 않았다. 이제 규칙과
정규식은 `parsing.roles` 한 곳에서 정의하고, Python `re`와 PostgreSQL `~`에서 같은 뜻으로 읽히게 번호 접두어는 대소문자를
구분하고 제목 단어만 `[Rr][Ee]…` 꼴로 쓴다. 생성되는 lexical SQL은 e1c813a 전후로 바이트가 같다.
- 골든 DB의 서로 다른 섹션 제목 4,855개와 합성 제목을 합친 379,877개에서 Python 함수, Python `re`, PostgreSQL `~`의
  판정이 같다. 옛 SQL은 합성 제목 6,930개에서 달랐고 코퍼스 제목에서는 0개였으므로 G1 차이는 없다.

F06(2ad7bb8): lexical 행은 SQL이 가져온 초록을 결과에 싣지 않아 `paper_abstract`가 늘 비었다. hybrid 병합 항목은 처음 본
채널 행의 사본이었고 lexical이 먼저 돌므로, 두 채널에 모두 나온 청크는 초록이 비고 vector 점수(`raw_similarity_score`,
`rerank_adjustment`)가 빠졌다. 이제 lexical 행이 초록을 싣고, 병합 항목은 두 채널의 점수 내역과 비지 않은 초록을 가진다.
점수, 순위, snippet, 문맥은 그대로다. G1 차이는 351개 중 상세 챗 hybrid 18개의 키 정보뿐이다(`keys` 6개, `uniform_keys`
12개). 상세 챗 hybrid hit 485개 중 52개가 두 채널에 모두 나온 hit이다.

**트레이드오프** — 단계를 공개 함수로 내면 평가 하네스가 private 메서드 대신 공개 이름에 묶인다. 제품 내부를 고쳐도
eval이 깨지지 않는 대신, 공개 함수의 시그니처를 바꾸면 eval도 함께 고쳐야 한다.
- `prepare=False`는 준비 문장 재사용(파싱·계획 비용 절약)을 포기한다. 옛 구현과 같은 계획을 얻는 쪽을 택했다.
- 벡터를 이진이 아닌 `%.12f` 텍스트로 보내 요청이 크다. 옛 구현과 같은 문자열을 보내 같은 벡터로 해석되게 했다.
- 제품 융합은 convex와 다양성만 둔다. 옛 가중 RRF로 되돌려 비교하려면 `arxplore_eval`의 research_fusion을 써야 한다.
- hybrid 요청 하나가 풀 연결을 최대 2개 쓴다. 옛 스레드 병렬과 같다.

**eval 영향** — 새 측정 지점은 다음과 같다.
- G1 변형 `tests/golden/data/g1_retrieval.v2.json.gz`(F06에서 처음 생김)와 `g1_retrieval.v2.diff.md`
- F05: `v2/tests/unit/retrieval/test_retrieval_reference_titles.py`(`test_sql_rule_agrees_with_the_chunk_role_rule` 등),
  `v2/tests/integration/retrieval/test_retrieval_lexical_pg.py::test_postgres_evaluates_the_title_rule_like_python`
- F06: `v2/tests/unit/retrieval/test_retrieval_convex_fusion.py`(`test_a_hit_found_by_both_channels_keeps_both_score_breakdowns`
  등)
- 실행 계획: `arxplore-eval explain`(6fa2ff2). 제품 빌더(`build_lexical_candidates_query`, `build_vector_search_query`,
  `resolve_hnsw_ef_search`)로 SQL을 만들고 제품 규칙(`hybrid_branch_limit`, `candidate_fetch_limit`)으로 LIMIT을 정해
  `EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`을 읽기 전용 트랜잭션에서 돌린다. 쓰인 검색 인덱스, Seq Scan, 계획·실행 시간을
  보고하며 옛 `scripts/explain_retrieval.py`를 대체한다.

**알려진 한계** — G1의 질의 벡터가 가짜라 vector·hybrid 순위는 실제 임베딩의 순위가 아니다. 실제 질의 임베딩 표로
다시 캡처하기 전까지 vector·hybrid의 실측 재현은 없다(09번 항목).
- 아래 전환점(후보 184개와 192개 사이)은 골든 코퍼스(임베딩 13,328개)의 값이다. 코퍼스 전환으로 청크와 임베딩이
  늘거나 통계가 바뀌면 다시 재야 한다. 제품 경로가 HNSW를 타기 시작하면 결과가 근사 검색이 되고 `hnsw.ef_search` 값이
  결과에 영향을 준다.
- `arxplore-eval explain`은 `hnsw.ef_search` 설정문을 따로 들고 있다(`arxplore_eval/explain.py`의 `HNSW_EF_SEARCH_SQL`).
  제품 쪽 문장이 바뀌면 함께 고쳐야 한다.
- F05 정규식은 Python과 PostgreSQL의 `\s`·`\d` 분류가 다른 문자(줄바꿈 없는 공백, 비ASCII 숫자)를 쓴 제목에서 판정이 갈릴
  수 있다. 코퍼스에는 없다.
- 이식 전후 검색 지연 비교는 결과 파일로 남기지 않았다.

**트러블슈팅** — 정확 검색으로 돌려도 G1 결과가 같았던 이유(벡터 1단계 전체 스캔)

- 증상: G1을 정확 검색(`GOLDEN_EXACT_SEARCH=1`, `enable_indexscan=off`)으로 돌려도 HNSW 인덱스가 있는 기본 실행과 결과가
  같았다. 옛 구현 캡처(e7a663f)와 v2 이식(04e19a7, 351/351) 모두 그랬다. HNSW는 근사 검색이라 인덱스를 다시 만들면 결과가
  바뀔 수 있어 두 벌을 확인하기로 한 것이었다.
- 원인: 이 코퍼스에서는 제품 경로의 벡터 1단계가 HNSW를 쓰지 않는다. 플래너는 1단계 후보 184개까지는 HNSW를 쓰고
  192개부터 전체 스캔과 정렬을 고른다. 제품 경로의 후보는 vector 검색(limit 5) 240개, hybrid 600개라 둘 다 임베딩
  13,328개를 모두 읽는 정확 검색이다. G1 평가 경로(k=10)의 후보 수는 같은 규칙(`candidate_fetch_limit`,
  `hybrid_branch_limit`)에서 이보다 많다.
- 확인 방법: `arxplore-eval explain`(6fa2ff2)으로 골든 코퍼스에서 후보 수를 바꿔 가며 벡터 1단계 계획을 봤다. lexical
  계획은 GIN 인덱스 두 개를 모두 쓴다.
- 해결: 코드는 바꾸지 않았다. 지금 제품의 벡터 결과가 정확 검색이라는 점을 기록하고, G1 정확 검색 변형이 같게 나오는
  이유로 삼는다.
- 재발 방지: `arxplore-eval explain`이 계획에 쓰인 검색 인덱스와 Seq Scan을 보고하므로 코퍼스나 후보 규칙이 바뀌면 다시
  확인한다. `v2/tests/integration/eval/test_eval_explain_pg.py`가 두 채널 계획, 읽기 전용 트랜잭션, 기대 인덱스 이름을
  검사한다.
